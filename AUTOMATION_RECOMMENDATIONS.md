## 🔌 MCP Servers

### context7
**Why**: The service leans on library-specific async patterns (SQLAlchemy 2.0 async sessions, pydantic-settings, FastAPI lifespans) plus `garminconnect`, a small unofficial wrapper around Garmin's private API whose usage patterns aren't well known to a general model. Live doc lookup avoids stale/guessed API calls when extending `garmin_client_factory.py` or writer/reader functions.
**Install**: `claude mcp add context7`

### Postgres MCP (e.g. `@modelcontextprotocol/server-postgres` or similar)
**Why**: Postgres is central here (asyncpg, goose migrations, `postgres-standards.md` / `postgres-service-test-standards.md`). A DB MCP pointed at your local dev DB (`PG_HOST=localhost`) lets Claude inspect actual schema/data when writing mappers or verifying a new goose migration, instead of inferring schema from migration files alone.
**Install**: `claude mcp add postgres postgresql://postgres:postgres@localhost:5432/health-dashboard-service` (point at your local dev DB only, never a staging/prod connection string)

## ⚡ Hooks

### Lint + format on save
**Why**: `ruff` (lint + format) is already the standard (`pyproject.toml`, `.pre-commit-config.yaml`), but currently only enforced at commit time and in CI. A `PostToolUse` hook on Edit/Write for `app/**/*.py` running `ruff check --fix` and `ruff format` gives instant feedback while Claude is still editing, instead of a failed pre-commit hook or CI run discovered later.
**Where**: `.claude/settings.json`
```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command", "command": "cd app && .venv/bin/ruff check --fix \"$CLAUDE_FILE_PATH\" && .venv/bin/ruff format \"$CLAUDE_FILE_PATH\"" }]
    }]
  }
}
```

### Block edits to real `.env` files
**Why**: `health_dashboard_service/.env` and `migrations/.env` hold real Postgres credentials and are gitignored on purpose (only `.env.sample` is committed). A `PreToolUse` guard prevents an accidental edit or read that could leak/overwrite local secrets — cheap insurance since Claude otherwise has no way to distinguish "the sample" from "the real file" except by name.
**Where**: `.claude/settings.json` (deny rule on `Edit|Write` for paths matching `**/.env` excluding `.env.sample`)

*(Skipped a "run tests on edit" hook: the suite uses `testcontainers[postgres]`, so tests spin up a real container — too slow to fire on every edit. `make test` / CI remains the right place for that.)*

## 🤖 Subagents

### test-writer (standards-aware)
**Why**: The project has unusually detailed, layered testing standards (`testing-standards.md`, `unit-test-standards.md`, `service-test-standards.md`, `postgres-service-test-standards.md`) with specific rules (polyfactory for fixtures, plain `assert`, resolve the unit the way production code does, no needless `async def` tests, 80% coverage). A dedicated subagent pre-loaded with those four files can generate tests matching house style more reliably than re-deriving the rules ad hoc each time, and can run in parallel to review coverage gaps after a feature lands.
**Where**: `.claude/agents/test-writer.md`

### migration-safety-reviewer
**Why**: CI already asserts migrations apply `up → down → up` cleanly, but that doesn't catch things like a destructive column drop without a backfill step, or a migration that isn't safe against in-flight rows (relevant here: a `drop_garmin_daily_stats_spo2_average` migration has already shipped). A subagent focused on goose migration safety (locking behavior, backward-compatibility with the currently-deployed app version, reversibility) is a narrow, high-value check distinct from the general `sc-code-review` standards gate.
**Where**: `.claude/agents/migration-safety-reviewer.md`
